# Discord: platform rules and how the adapter encodes them (workstream ES)

Sources read on 2026-11-26 (read-only fetches of public documents; no Discord API call was made):

* Discord Community Guidelines — https://discord.com/guidelines
* Discord Developer Policy (effective 2024-07-08) —
  https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy
* API reference, rate limits / guild / invite / guild scheduled event —
  https://github.com/discord/discord-api-docs (`developers/topics/rate-limits.mdx`, `developers/resources/*.mdx`)
* For the administration tools and the Gateway window (read 2026-11-27, commit `62ab2d5` of the same repository):
  `developers/topics/permissions.mdx` (permission bits, the permission algorithm, timed-out members),
  `developers/topics/opcodes-and-status-codes.mdx` (gateway opcodes, close codes, JSON error codes),
  `developers/events/gateway.mdx` and `gateway-events.mdx`, `developers/resources/{guild,channel,message,invite,
  audit-log,user,application,guild-scheduled-event}.mdx`, `developers/reference.mdx` (snowflake time, audit reason).
  Every route, field name, permission bit, intent bit, opcode and close code in the adapter is transcribed from
  these files.

The operator must re-read these before activating the live integration; they change. Nothing below is legal
advice. Content rules (what may be said) are enforced by the authorization service (EA) and the operator's
approval of publications, not by this adapter; the adapter encodes the *mechanical* constraints.

## Administration tools and the Gateway window (added 2026-11-27)

Rows marked *operator* are constraints the operator set for CAM, stricter than the platform's rules; the others
continue the table above.

| Rule | What it requires | Where it is encoded | Test |
|---|---|---|---|
| *Operator*: no operation on a member; Developer Policy 1, 2 (do not modify accounts or act on a server's behalf without permission) | CAM manages the server's structure, never its people | No tool and no client method gives or takes a role from a member, removes, bans, times out or renames a member, or writes to one. `create_role` / `modify_role` / `delete_role` act on the role itself ("it is not given to anyone"); `set_channel_permissions` writes overwrite type 0 (role) only and first verifies that the id is a role of the server, so a member id cannot be passed off as one. The only member route in the source is a `GET` of the bot's **own** member object (its roles, for the permission check). No schema has a field that could carry a member | `test_es_discord_admin.py::test_no_tool_names_or_takes_a_member_as_target`, `::test_channel_create_modify_permissions_delete`, `::test_roles_create_modify_delete_and_the_refusal_list` |
| *Operator*: permission scope | CAM uses only the Discord permissions the operator listed, whatever the bot's role would allow | `DiscordExecutor(scope=...)` / `resources.discord.scope` (default: the 18 permissions of integer 2269727275740401). Every tool carries the permissions its route needs (`TOOLS[name].requires`, from the route's documentation); a tool that needs one outside the scope is `available=False` ("outside the operator's permission scope: needs ...") and executing it is refused before any request and before any check — also when the bot is ADMINISTRATOR. `get_permissions` reports what the role holds beyond the scope (`broader_than_scope`) | `::test_scope_refusal_even_when_the_bot_is_administrator`, `::test_get_permissions_agrees_with_the_service_for_roles_and_overwrites` |
| *Operator*: nothing dangerous is handed out | A role or overwrite created by CAM must not be able to act on members, on the server or on everyone | `ADMINISTRATOR`, `KICK_MEMBERS`, `BAN_MEMBERS`, `MODERATE_MEMBERS`, `MANAGE_GUILD`, `MANAGE_ROLES`, `MANAGE_WEBHOOKS`, `MENTION_EVERYONE` are refused (`INVALID_ARGUMENTS`, nothing sent) in a role's permissions and in an overwrite's `allow`, as is any name outside the scope. The `@everyone` role and integration-managed roles are never modified or deleted. A created role always states its permission set (an omitted one would default to the permissions of `@everyone`) | `::test_roles_create_modify_delete_and_the_refusal_list`, `::test_channel_create_modify_permissions_delete` |
| Developer Policy 1, 2; act only in the owner-authorized server | Nothing of another server is changed | Channels, the system / rules / updates channel of `modify_guild`, messages and pins must belong to the authorized guild; `delete_invite` reads the invite first and refuses one whose guild is another; a role id must be a role of the guild. `get_identity` reports the number of other servers the bot is in (a count, never their names or ids) as a warning | `::test_delete_invite_only_of_the_authorized_guild`, `::test_delete_pin_and_unpin_messages`, `::test_rename_guild_and_restore`, `::test_identity_other_guilds_and_missing_capabilities` |
| Developer Policy "API Limits" (avoid invalid requests: 401 / 403 / 429) | Do not send requests that will be refused | The bot's effective permissions are computed with the documented algorithm (`@everyone` \| roles; ADMINISTRATOR = all; channel overwrites in the documented order; timed-out members) from `GET /guilds/{id}/roles` and the bot's own member object, cached 300 s; a request the bot lacks a permission for is not sent ("the bot lacks ... in this server; the server owner must grant it"). A 403 that arrives anyway drops the cache. An invite list without use counts is reported as the missing `MANAGE_GUILD`, never as zero uses | `::test_permission_algorithm_roles_everyone_administrator_overwrites`, `::test_precheck_refuses_without_the_doomed_request`, `::test_a_403_that_arrives_anyway_drops_the_cached_permissions` |
| Gateway documentation (Identify limit: 1000 per day, "the bot token will be reset" on exceeding it; rate limit 120 events per 60 s) | Use sessions sparingly | One Identify per window, no resume and no reconnect (opcode 7 / 9 end the window and are reported); `GET /gateway/bot` is read first and no session is started when `session_start_limit.remaining` is at or below the reserve (50); a window lasts 1-60 s and keeps at most `max_events` events; an intent the application does not have is detected from `GET /applications/@me` before Identify, so no session is spent on a 4014 close; close codes 4004 / 4013 / 4014 are hard failures with their documented meaning | `test_es_discord_gateway.py::test_reconnect_invalid_session_and_refused_identifies`, `::test_listen_events_hard_failures_limits_and_destinations`, `::test_heartbeats_jitter_ack_request_and_a_connection_that_stops_answering` |
| Developer Policy 15, 16, 20 (use API data only as necessary; no profiling; no scraping) — **which intents are requested and why** | Receive only what the objective's measurement needs | `GUILDS` (the guild's own state: Guild Create / Update, channel changes), `GUILD_MEMBERS` (privileged: members joining, leaving, passing screening — the quantity the objective is about), `GUILD_INVITES` (invites created / deleted), `GUILD_MESSAGES` (that a message was posted, where, by a person or a bot, and its length), `GUILD_SCHEDULED_EVENTS`. `MESSAGE_CONTENT` only when `data_permissions["discord_message_content"]` is true. Never `GUILD_PRESENCES` (who is online is not needed), never any `DIRECT_MESSAGE*` intent, no typing, reactions, voice or moderation intents: `GatewayWindow` refuses to be constructed with the forbidden ones | `::test_protocol_constants_come_from_the_documentation`, `::test_listen_events_through_the_executor` |
| Developer Policy 15, 16, 19, 20 — **data minimisation of events** | Aggregates and pseudonyms only | Events are reduced inside `discord_gateway` before anything leaves it: Ready -> number of guilds; Guild Create -> member and channel counts; member events -> `{id_hash, bot, joined_at, pending, test_account}`; invites -> code, channel, limits (no inviter); messages -> channel, author pseudonym, bot flag, length (text only under the content permission); channels and scheduled events -> id, name (type). An event of any other guild is counted and dropped; an event without a guild (a direct message) is dropped; every other event type is counted by name and dropped. `get_member_events` returns counts and the join times of new people from a diff of two pseudonymous snapshots; the snapshot file (0600) holds no raw id. `get_audit_summary` returns counts per kind of action and two times: no actor, no target, no reason | `::test_window_receives_member_add_and_remove_and_reduces_them`, `::test_invites_messages_channels_and_scheduled_events_are_reduced`, `::test_events_of_other_guilds_are_counted_and_dropped`, `test_es_discord_admin.py::test_member_event_diff_baseline_bots_and_declared_test_accounts`, `::test_audit_summary_has_counts_and_times_only` |
| Developer Policy 21 (message content) | Message text does not reach the learner by default | In a window, text is kept only with the content permission, and then the read is put to the authorization service as its own operation `discord.read_messages` before anything connects; without the intent the Gateway delivers empty content anyway | `test_es_discord_gateway.py::test_listen_events_with_the_content_permission_is_its_own_checked_read` |
| Developer Policy 4 and credential hygiene | The token is sent to Discord and to nothing else, and is visible nowhere | The token is requested from the broker for the gateway URL as destination (the operator binds the secret to both destinations); against `discord.com` only a `wss` address under `discord.gg` is accepted. It is sent in Identify only, is not kept on any object, is removed from the text of every exception (which carry no chained original), and the websocket library's frame logging is disabled for the connection | `::test_the_token_is_in_no_exception_and_no_result`, `::test_listen_events_hard_failures_limits_and_destinations` |
| Transparency towards the server's owner (audit log documentation: `X-Audit-Log-Reason`) | The owner can see which changes the bot made on CAM's behalf | Every write whose route supports the header carries `X-Audit-Log-Reason: CAM Live authorized action`; every write passes `ExecContext.check` with deterministic arguments; deleting another author's message is put to the check a second time with `own: false` | `test_es_discord_admin.py::test_every_new_write_tool_passes_through_the_check_with_deterministic_arguments`, `::test_delete_pin_and_unpin_messages` |

Not covered here and required before live use: the application must be created by the operator in the Discord
Developer Portal and invited to the server by its owner; the *Server Members* privileged intent must be granted
for exact member counts (without it the adapter reports only Discord's approximate counts and says so); the
operator must provide users a way to report issues with the application (Developer Policy, section after rule 14);
`DiscordExecutor(user_agent=...)` should name the application's URL as Discord's reference asks.
For the administration tools and the Gateway window: the owner adds the bot with the permissions of the scope
(integer 2269727275740401 for the default scope) and the bot's role must be above the roles it is to edit; the
*Server Members* intent must be enabled for `listen_events` and `get_member_events` (and *Message Content* only if
the content permission is on record); the secret must be bound to `gateway.discord.gg` as well as `discord.com`;
permissions the documentation marks with `*` (`MANAGE_CHANNELS`, `MANAGE_GUILD`, `MANAGE_MESSAGES`, `MANAGE_ROLES`,
`MANAGE_THREADS`) need two-factor authentication on the application owner's account in a server that enforces 2FA
for moderation — the adapter cannot see that setting, and such a request fails with a 403.

**Staging.** Everything above was exercised against `cam_live.harness.staging_discord` (a local imitation of the
REST subset used and, since 2026-11-27, of the Gateway). No request has been sent to Discord by this workstream's
code or tests. The fidelity of the imitation to the real service is unverified beyond the published
documentation: in particular the exact error codes for role-hierarchy and managed-role refusals, the behaviour of
`GET /guilds/{id}/invites` without `MANAGE_GUILD`, and the timing of Gateway events are the imitation's reading
of the documentation. `tools/discord_live_check.py` is the check against the real service; it has been run in
`--staging` only (`docs/evidence/ES/discord_live_check_staging.json`). Observations built from the staging service
carry `provenance.source = "discord:staging"`, `data["staging"] = true` and a `[staging]` text prefix.
