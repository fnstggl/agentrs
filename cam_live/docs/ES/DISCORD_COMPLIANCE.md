# Discord: platform rules and how the adapter encodes them (workstream ES)

Sources read on 2026-11-26 (read-only fetches of public documents; no Discord API call was made):

* Discord Community Guidelines — https://discord.com/guidelines
* Discord Developer Policy (effective 2024-07-08) —
  https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy
* API reference, rate limits / guild / invite / guild scheduled event —
  https://github.com/discord/discord-api-docs (`developers/topics/rate-limits.mdx`, `developers/resources/*.mdx`)

The operator must re-read these before activating the live integration; they change. Nothing below is legal
advice. Content rules (what may be said) are enforced by the authorization service (EA) and the operator's
approval of publications, not by this adapter; the adapter encodes the *mechanical* constraints.

| Rule | What it requires | Where it is encoded | Test |
|---|---|---|---|
| Guidelines 14 "Do not use self-bots or user-bots" | Only an application bot may be automated | `DiscordClient` sends `Authorization: Bot <token>` and has no other scheme; no login, user-token or gateway code exists | `test_es_discord.py::test_auth_header_user_agent_and_staging_label`, `::test_executor_tools_describe_capabilities_only` |
| Guidelines 13, Developer Policy 5, 6, 7 (no unsolicited bulk messages; no contacting users without permission; no advertising to users; no contact outside Discord using API data) | No direct messages; no contact data leaves the adapter | No DM endpoint (`/users/@me/channels`) or DM tool; a channel of type DM / group DM, or any channel that is not in the authorized guild, is refused before a request about it is made; member objects are reduced before they leave the client, so no username, id or contact handle is available to the agent | `::test_direct_messages_and_other_servers_are_never_touched`, `::test_members_bots_and_declared_test_accounts` |
| Guidelines 15, Developer Policy 13 (no inauthentic engagement; no inflating membership with bot or user accounts; no automated messages "for the purpose of maintaining activity") | Counts must not be inflated; the adapter must not manufacture activity | Bots, pending members and operator-declared test accounts are counted separately from people (`member_counts`); no tool adds members or accepts invites; the adapter has no scheduler, timer or repeat option — a message is sent only when an authorized action asks for that one message; every send passes `ExecContext.check` (authorization, rate limits, approval) | `::test_members_bots_and_declared_test_accounts`, `::test_stats_messages_invites_through_the_executor`, `::test_denials_platform_rules_and_missing_permissions_are_hard_failures` |
| Developer Policy 1, 2 (do not modify accounts or act on a server's behalf without permission) | Act only in the owner-authorized server | One guild id per executor, fixed in every tool's schema (`guild_id` is a `const`); without it the tools are `available=False` ("blocked: no owner-authorized Discord guild is configured") | `test_es_integration_shapes.py::test_discord_tools_name_the_server_and_use_a_probe_for_availability`, `test_es_discord.py::test_tools_are_unavailable_without_credentials_and_nothing_is_sent` |
| Developer Policy 15, 16, 20 (use API data only as necessary; no profiling of users or their relationships; no mining or scraping) | Data minimisation; aggregates only | `list_members` returns only `{id_hash, bot, joined_at, pending, test_account}`; channel activity returns counts; invites drop the inviter; nothing per-person is turned into an observation; there is no member search, no message search and no bulk export tool | `::test_members_bots_and_declared_test_accounts`, `::test_message_content_is_dropped_by_default` |
| Developer Policy 19 (do not re-identify or reverse hashes) | Pseudonyms are one-way and are never resolved | `member_id_hash` = SHA-256 of salt, guild and user id; the library contains no reverse mapping and stores no raw id | `::test_members_bots_and_declared_test_accounts` |
| Developer Policy 21 (do not train models on message content obtained through the API without Discord's express permission) | Message text must not reach the learner by default | Message text is dropped inside `DiscordClient.channel_activity`; it is returned only when `TaskSpec.data_permissions["discord_message_content"]` is true (the operator asserts the permission is on record), and then the read is put to the authorization service as its own operation `discord.read_messages`; authors stay pseudonymous either way. The API's echo of the bot's own message is not turned into an observation | `::test_message_content_is_dropped_by_default`, `test_es_integration_shapes.py::test_retaining_message_text_is_put_to_the_policy_as_its_own_operation` |
| Developer Policy "API Limits" and the rate-limit documentation (parse the headers, do not hard-code limits, do not circumvent; avoid invalid requests: 401 / 403 / 429) | Honour limits; stop after refusals | Limits are read from `X-RateLimit-*` / `Retry-After` / the 429 body; an exhausted bucket is waited for (bounded) before sending; a 429 is repeated only after `retry_after`; a global limit blocks every route; a wait above the bound is reported as `RESOURCE_LIMIT` and nothing is sent. 401 / 403 are `MISSING_PERMISSION`, platform maxima and platform-rule error codes are `PLATFORM_RESTRICTION`; both are HARD: never retried, and the modality selector blocks the intent instead of trying another route. One token only; no token rotation | `::test_rate_limits_are_read_from_headers_and_waited_for`, `::test_rate_limited_and_unreachable_service_through_the_executor`, `::test_denials_platform_rules_and_missing_permissions_are_hard_failures`, `test_es_modality.py::test_a_refusal_never_causes_a_modality_switch` |
| Developer Policy 4 (never collect credentials) and credential hygiene | The token is never visible to the learner | The token is named, not held: it is fetched from the secret broker at the moment of each request and appears in no `PrimitiveOp`, `Observation` or log written by the adapter | `test_es_integration_shapes.py::test_discord_tools_name_the_server_and_use_a_probe_for_availability` |
| Guidelines 16-23, Developer Policy 8-12 (content and conduct rules) | Published content must comply | Out of the adapter's scope by design: content is whatever the agent wrote; it reaches the authorization service verbatim in the checked operation (`content` and its SHA-256), where platform-compliance rules and the operator's approval apply | `test_es_discord.py::test_stats_messages_invites_through_the_executor` (the policy receives the literal text) |

Not covered here and required before live use: the application must be created by the operator in the Discord
Developer Portal and invited to the server by its owner; the *Server Members* privileged intent must be granted
for exact member counts (without it the adapter reports only Discord's approximate counts and says so); the
operator must provide users a way to report issues with the application (Developer Policy, section after rule 14);
`DiscordExecutor(user_agent=...)` should name the application's URL as Discord's reference asks.

**Staging.** Everything above was exercised against `cam_live.harness.staging_discord` (a local imitation of the
REST subset used). No request has been sent to Discord. Observations built from the staging service carry
`provenance.source = "discord:staging"`, `data["staging"] = true` and a `[staging]` text prefix.
