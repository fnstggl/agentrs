# D3: class-4 semantic participants, model routing, structured representations (wave 3b)

Workstream D (wave 3b, branch `c5c/w3b-sem`). Covers MASTER_SPEC 3.2 class 4, 3.3, 4.2-4.3, 13.4-13.5 and Gates E
and H. Numbers come from unofficial runs on this branch (see `docs/v5/workstreams/D.json`); official evidence is
produced later on the integration branch by the canonical gate tests.

## Class 4 of the population (`crucible.semantic.generalists`)

The semantic participants are the class-4 rows of the one population (`crucible.population`, D-15): kernel module
`pop_semantic` calls `population.register_class_runtime(world, 4, ...)` in `install`, so the population's tick hands
every due class-4 row to the runtime and records the session as for any individual. A participant therefore has
the population's persistent identity (principal `p<i>`, bank account, interests, skills, preferences, contacts,
income) plus its own mind state in table `semp_state` (persona, goals with status, memory, action history, known
identifiers, perception cursors, counters), written only by the appliers of `semp.agent` and `semp.update`. Nothing
lives on a Python object between activations; snapshots, forks, replay and regeneration carry it.

One activation (`mind.activate`, batched across the participants due in the same tick):

1. **perceive** - read-only tools as the participant itself: `bank.accounts`, `pop.me`, unread `mail.inbox`
   headers, `aud.mine` analytics of its own items; its whole tool interface (`World.available_tools`).
2. **goal** - without an active goal, the participant writes one sentence ("I will ...") from its persona (derived
   from its population row: nearest interest topics, skills, traits, employment, income), its needs (money, unread
   mail, how long since it created or talked to anyone) and memory. No goal is assigned anywhere.
3. **act**, up to three times: it names its next action in general words (or says stop / wait), the service
   directory is searched for that phrase (MiniLM similarity of each service's best tool, the goal, BM25), it chooses
   a service, then a tool of that service, then each argument slot: enum and boolean values, numbers and identifiers
   it has seen (by kind: accounts, people, messages, artifacts, content) are chosen; free text, JSON and code are
   written. The call runs with `ctx.call(tool, args, as_principal=<its principal>)`; refusals and tool faults come
   back as results it remembers.
   * "stop" (goal achieved) and the `finish` service are offered only once a call for the goal has succeeded, and
     "wait" only once the participant has sent something to others for it (`awaiting`; offered after any action,
     the participants of the first standard run waited out most goals: 17 calls in 72 activations): in the first LM society (Qwen3-0.6B on every route, 1.5
     days) every fresh goal was declared achieved before any action (33 goals, 0 calls). An unoffered answer makes
     the goal itself the search query. The intent prompt carries no example phrase (the 0.6B model copied it).
   * The content of a publication (`ref` of `*.publish` / `content.update`) is either an artifact the participant
     already made or text it writes in that call (`COMPOSE`): the runtime stores the text as the participant's own
     artifact with `studio.write` inside the same decision, as a publishing form offers a text box. Without it the
     participants passed invented references (`ref: "studio_p1040"`) and every publication was refused.
   * A refused call undoes the whole decision, including text stored for it, and the participant forgets the
     identifier of that text. Written values are discarded (`copied_values`, `mind.copied_from_prompt`) when they
     echo the prompt's scaffolding ("You are calling ...", "Next argument ..."), name a tool or service (a short
     value: the called tool, its service or any tool; a longer text: any tool or service - the audit's 'cal' titles
     and 'mail.send' bodies), restate the participant's goal sentence, or announce instead of saying (a title that
     prefaces, "Here is the text you'd publish:"; a composed publication that says next to nothing once its
     announcing sentences, "I will publish an article on ...", are left out: both seen in the fourth standard run);
     a short value (title, query, board ...; not a subject, which may repeat the subject it answers) of four words
     or more when more than half of its word 4-grams occur in the prompt outside the participant's own words (its
     goal and the values it wrote in its recent calls: another person's title, the tool description, a memory line,
     the persona); a longer value when more than 30 % of its word 5-grams occur
     outside its own words, and a composed publication also when more than half occur anywhere in the prompt, goal
     included (verifier probes P1/P1b: the repair of 2a6fd4d had let such copies through). A title about the goal
     still reuses its words freely (the third standard run had discarded 48 such values of one participant and every
     one of its publications was refused for a missing title). A required value written unusably is written once
     more by sampling (`rewritten_values`). Next-step phrases that are written-out tool calls fall back to the goal as the query.
     Retrieval queries drop identifiers and numbers, and a service also matches by its directory summary.
   * Identifier options are checked against the argument's kind: a publication offers only artifacts the
     participant made itself (`seen.own_refs`: texts it wrote, artifacts its own non-read-only calls stored in its
     name, and results that name it as the owner - never another participant's artifact it only read with
     `artifact.info` / `artifact.get`, verifier probe P4; the third run published others' artifacts 17 times, "you
     can only publish artifacts you own"); an object argument
     (listing, offer, thread, ...) never takes a person; optional addressees (`to` of `msg.send`, which takes either
     `to` or `conversation`) are offered among the people it knows.
4. **persist** - one `semp.update` with what the activation added. A fault of the runtime itself (for example the
   model running out of the slot's GPU memory) undoes the activation and is counted (`activation_faults`) instead of
   failing the population's tick: in the second standard run such a fault, retried at every tick, froze all eight
   participants after day 1 (13 activations, 6,950 model requests). The service bounds the key/value-cache rows of
   one forward pass (`kv_token_budget`), since every option row of a choice carries a copy of its prompt's cache.

Every model call is recorded (`crucible.substrate.inference.recorded`, through `SemanticService.choose/generate`
with the transaction's ctx; shortlists through `catalog.recorded`), so replay and regeneration never run a model.

`brain="ablated"` replaces every model decision by a uniform random one with the same inputs (SP-3.2d ablation).

Evaluator side (`generalists.verify`, never in-world): actions joined with the events they emitted (consequential =
succeeded, not read-only, visible to another principal or the public); provenance (every event acted as a
participant must lie inside a brain-chosen call); productive results (published items viewed by at least three
independent individuals, exact audience sets); collaborative results (on-topic replies to another participant's
request, co-edited documents, payments between participants who talked); binding to population rows.

Held-out tool selection (`generalists.bench`): situations of a real class-4 participant in a civilisation, staged
with real tool calls, decided by the same `mind.decide` over all of its tools; `dev` templates were used while
designing prompts and retrieval, `test` templates only for measurement.

## Model routing (`crucible.semantic.routing`, DECISION_LOG D-36, D-37, D-38)

D-38: an in-situ measurement may name a reasoning-first variant `<model>#think<N>` (the Qwen3 model reasons in its
own thinking mode for at most N tokens, then names an option, else the options are scored after its closed
reasoning: `participants.select_options`, both requests recorded); `derive` keeps the smallest effective
checkpoint and, at equal size, the plain choice first. The decision stores `think_tokens` per capability and
`LMBrain` applies it (`routing.think_tokens`). Gate H.n1 measures the largest model serving the decisions of every
activation (situation interpretation, tool choice, writing, content understanding) and asserts that decisions
escalated above 1.1B parameters stay at most 20 %.

D-37 adds in-situ measurements (`routing.derive(report, in_situ)`, same smallest-effective rule): tool choice on
the class-4 bench's DEV templates (Qwen3-0.6B 0.58, Qwen3-1.7B 0.68 -> 1.7B) and writing on the DEV situations
(share of publication texts not copied from the prompt: SmolLM2-135M 0.42, SmolLM2-360M 1.00 -> 360M). Current
routes: content understanding Qwen3-0.6B; situation interpretation, tool choice, incentive adaptation,
negotiation, programming, strategy Qwen3-1.7B; writing SmolLM2-360M. H.n1 therefore reports 1.7B (fails the ~1B
target by measurement).


`data/routing.json` is derived from the measured SP-3.2b report (held-out templates, smallest effective model per
capability, else the best measured): content understanding and tool choice Qwen3-0.6B, communication SmolLM2-135M,
situation interpretation, incentive adaptation, negotiation, programming and strategic decisions Qwen3-1.7B. One
process-wide service per model; GPU placement only within the slot's grant, counting the models already placed and
sharing a copy already on the GPU. `routing.model_card` reads licences from the local model cards (all four:
apache-2.0); `routing.tool_use` verifies tool use by running each checkpoint (native tool-call template and calls;
choice-based selection as participants use it).

## Shared space changes

* Images from participants are decoded in the jail (`crucible.sandbox.isolation.decode_image`, pixel-identical;
  O.json W.1 / SP-16b) - `media.open_image`.
* `space_feed` (`semantic/feedprobe.py`): a Gate E.3 probe through the social internet's feeds.
* `structured.py`: structured representations of software (code facts) and products (public page).
* `lm_fast.py` / `distill.py`: a cheaper LM feature candidate (SmolLM2-135M coherence, valence head distilled from
  Qwen3-0.6B on 9,654 texts) with a held-out equivalence report (`space/maps/valence_head_report.json`, 2,400
  held-out texts): valence Pearson 0.752, coherence Spearman 0.887, novel coherence 0.886, TEST negation/polarity
  direction 12/12, 2.6x faster per text on the GPU (about 7x on one CPU thread). The adoption rule
  (`lm_fast.ADOPTION`: valence Pearson >= 0.85, coherence Spearmans >= 0.9, >= 11/12 pairs) is not met, so the space
  keeps Qwen3-0.6B; the CPU cost of the text path (about 1.4-3.5 s per text on one thread) remains, and population,
  social and civilisation runs belong in GPU slots (0.01 s per text). int8 dynamic quantization of Qwen3-0.6B on CPU
  was also measured and is not equivalent (valence Pearson -0.32 on DEV sentences).
* DEF-P-25: the space version is derived without importing huggingface_hub or probing CUDA.
