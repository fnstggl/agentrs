# E2: empirical calibration of commercial response and software adoption

Workstream E2 fitted three behavioural models on public data and evaluated each one on held-out data against a simple
baseline:

* `commercial_response@1` is fitted on a randomized experiment (Criteo Uplift v2.1). Its effects are experimentally
  identified.
* `software_deep_engagement@1` and `software_repo_growth@1` are fitted on GH Archive, public GitHub activity from
  2024-10-07 to 2024-10-10. Both are observational.

World code loads a model through the registry and never touches a dataset. The commercial model is built for the
simulator to use; the two software models give developer behaviour a measured reference.

## How to use it

```python
from crucible.calibration.registry_e2 import load
ad = load("commercial_response@1")
types = ad.sample_types(rng, n)                      # once per simulated individual (store in a column)
table = ad.transport(control_visit_rate=0.05)        # optional: re-base to the world's own rates
r = ad.respond(rng, types, treated_mask, table)      # {'visit': bool[n], 'conversion': bool[n]} per campaign period

deep = load("software_deep_engagement@1")
p = deep.predict(deep.matrix_from_counts({"repo_stars_24h": ..., ...}))   # P(fork/issue/PR within 24 h | first star)
growth = load("software_repo_growth@1")
stars_tomorrow = growth.sample(rng, growth.matrix_from_counts({...}))      # NB2 draws around predict()
```

Each card's `simulator_mapping` states which simulator quantity feeds each input, its unit and its transform. The
population and innovation workstreams should implement exactly that mapping.

## Commercial intervention response (Criteo Uplift v2.1)

**Data.** `criteo-research-uplift-v2.1.csv.gz` comes from the Criteo-owned Hugging Face repository
`criteo/criteo-uplift`, revision `2424920`. The original go.criteo.net link returned 404.

* SHA-256 `2716e1bf...16dc`; license CC BY-NC-SA 4.0. Fitted parameters are shared under the same terms,
  non-commercially, with attribution to Diemert et al., AdKDD 2018.
* 13,979,592 users, 12 anonymised features. Treatment ratio 0.85, visit rate 4.70%, conversion rate 0.29%.
  Exposure among treated users is 3.6%.
* Schema checks: no NaNs, every label binary, no exposure in control, no conversion without a visit.

**Identification.** Treatment was randomised within each pooled incrementality test, so the per-arm models identify
intention-to-treat effects conditional on the features. A post-fit diagnostic found that treatment ratios differ
slightly between the pooled tests:

* the propensity AUC on validation is 0.509;
* the propensity ranges from 0.844 to 0.894 between q01 and q99;
* the largest feature |SMD| is 0.048, against about 0.001 expected under pure randomisation.

As a result, the raw difference in means overstates the average effect. On the test split:

| estimate | visit effect | conversion effect |
|---|---|---|
| raw difference in means | 0.0103 (se 0.0003) | 0.00124 |
| model-implied standardised | 0.0074 | 0.00096 |
| propensity-stratified (18 tie-safe strata) | 0.0077 [0.0071, 0.0083] | 0.00107 [0.00091, 0.00123] |
| IPW | 0.0075 | 0.00111 |

The exposure (complier) Wald estimates in the report use the raw ITT, so they inherit the same upward bias:

* visit: 0.285 raw, about 0.21 when computed from the standardised ITT;
* conversion: 0.034.

**Models.** The baseline is a constant effect: per-arm training rates. The T-learners have two complexities, logistic
and histogram GBDT. Amendment 1 added a regularised GBDT, because the prespecified GBDT's treated-arm conversion
model diverged at its second Newton step. That model now keeps its best iteration, which is one tree.

The split is a seeded 60/20/20 row split, which is a user-level holdout; the data have no timestamps. Test results on
2,795,919 users:

| candidate | primary (visit + conv. log loss) | visit LL | conv. LL | visit ECE | conv. ECE | visit AUC | conv. AUC | Qini visit | Qini conv. |
|---|---|---|---|---|---|---|---|---|---|
| constant effect (baseline) | 0.20915 | 0.18914 | 0.02001 | 0.0232 | 0.0014 | 0.515 | 0.527 | 0 | 0 |
| T-logistic | 0.12394 | 0.11127 | 0.01267 | 0.0079 | 0.0004 | 0.932 | 0.948 | 0.089 | 0.200 |
| T-GBDT (prespecified) | 0.12152 | 0.10250 | 0.01902 | 0.0004 | 0.0026 | 0.947 | 0.926 | 0.084 | -0.039 |
| **T-GBDT regularised (kept)** | **0.11426** | **0.10244** | **0.01182** | **0.0004** | **0.0001** | **0.947** | **0.958** | 0.087 | 0.159 |

Bootstrap comparisons of the kept model (kept minus other, 200 paired resamples):

* against the baseline: -0.0949 [-0.0955, -0.0942];
* against T-logistic: -0.0097 [-0.0099, -0.0095];
* against the prespecified T-GBDT: -0.0073 [-0.0075, -0.0070].

`worse_model_kept` = 0. Per-arm calibration is close: mean predicted against observed is 0.0383/0.0381 for control
visits and 0.0485/0.0485 for treated visits. On uplift ranking, the secondary metric, the kept model does not beat
T-logistic: visit Qini 0.087 [0.081, 0.093] against 0.089, conversion Qini 0.159 [0.132, 0.190] against 0.200.

**Heterogeneity.** The predicted visit effect is concentrated in a small segment:

* quantiles: q50 0.0004, q95 0.048, q99 0.137;
* the top predicted decile shows 0.066 predicted against 0.058 observed;
* deciles 2-8 are near zero both predicted and observed;
* the 16.5% of users with negative predicted effects are not confirmed: the lowest decile shows -0.006 predicted
  against +0.004 observed.

**Response types (for the simulator).** The table has 64 types: 8 equal-mass bins of predicted control visit
probability, times 8 bins of predicted visit effect, built on validation. Held-out validation on test:

* type-level weighted correlation of predicted and observed visit uplift: 0.970 [0.948, 0.978];
* calibration slope 0.84 (the model's extreme types are a little too extreme);
* conversion correlation 0.980;
* acceptance rule (prespecified: lower bound > 0) passed, `usable` = true.

The table's average effect (0.0074) agrees with the propensity-stratified estimate (0.0077 ± 0.0003).

`response_types("honest")` uses the rates observed on validation within each cell instead of the model means. It
scores better on test: correlation 0.988, slope 1.006, weighted MAE 0.0017 against 0.0029. This is a secondary
analysis that the plan did not choose, so the default stays `"model"`. Population owners may pick `"honest"`,
knowing that this comparison used the test split.

**What the simulator may and may not infer.** The simulator may use:

* the relative structure of ad response: most individuals barely respond and a small segment responds strongly;
* the correlation between baseline propensity and effect;
* the odds-ratio form, through `transport`.

It may not use:

* the absolute rates. Criteo sub-sampled non-uniformly to hide incrementality;
* the feature-level model, because the features are anonymised;
* any carry-over, frequency, saturation, price or creative effects;
* any response to content or interventions other than eligibility for one advertiser's display campaign during one
  test period.

## Software adoption (GH Archive, observational)

**Data.** GH Archive keeps hourly dumps of the public GitHub events API. E2 used the 96 hours from
2024-10-07T00 to 2024-10-11T00 UTC: 22,011,349 events from 9.8 GB of raw files. Each hour was streamed, checked
against its SHA-256 and reduced to a 160 MB compact table. Only numeric actor and repository IDs and event type and
action were kept, plus four derived flags (org, bot, owner, repo-creation) and push size. No logins or text were
kept.

The 2024 window was chosen because it is complete. The 2025-10 and 2026-10 dumps carry 2.0x and 30x fewer stars per
hour, a sign of changes in the events API.

**Population.** Public GitHub accounts and repositories whose events reached the public API. `[bot]` accounts are
excluded from the units. The population skews towards professional developers and some regions and time zones. It
includes automation that is not marked as a bot, and stars inflated by star farming.

### `software_deep_engagement@1`

Each unit is a developer's first star on a repository they do not own. 376,446 units fall in the train, validation
and test periods.

The label is whether, within 24 h, the same account forks the repository, files or comments on an issue, or opens or
reviews a pull request. Label rates: 3.86% in train, 4.10% in validation, 3.25% in test. By kind on test (kinds overlap):
fork 2.6%, issue 0.6%, pull request 0.4%.

There are 19 features, all computed from the 24 complete hours before the star.

The holdout is time-based: train on D1, validate on D2 00-12, test on D2 12-24.

Held-out results on the test split (83,304 stars):

| candidate | log loss | Brier | ECE | AUC | AP |
|---|---|---|---|---|---|
| constant rate (baseline) | 0.14393 | 0.03150 | 0.00625 | 0.500 | 0.033 |
| L2 logistic | 0.13223 | 0.03105 | 0.00511 | 0.727 | 0.133 |
| **GBDT (kept)** | **0.12686** | **0.02969** | 0.00527 | **0.737** | **0.157** |

Bootstrap comparisons: kept minus baseline log loss is -0.0171 [-0.0186, -0.0152]; kept minus logistic is -0.0054
[-0.0062, -0.0044]. `worse_model_kept` = 0.

Robustness checks:

* **User-level holdout.** On 58,701 test stars by developers never seen in train or validation, the kept model scores
  0.1351 against 0.1475 for the baseline (AUC 0.686).
* **Strict time check.** Refitting on D1 00-12 only, so that every training label closes before the test period,
  gives 0.1267 on test.

Calibration: ECE is 0.005, but the top predicted decile over-predicts (0.169 predicted against 0.131 observed). The
test period's base rate (3.25%) is below the training base rate (3.86%).

### `software_repo_growth@1`

Each unit is a (repository, day) pair with at least one star or fork that day, or a repository created that day. The
target is non-bot stars on the next day. There are 11 features.

Splits:

* train and validation are D1 to D2 (264,438 and 66,267 repositories, split by repository hash);
* test is D2 to D3 (321,303 rows, time-based).

| candidate | mean Poisson deviance | MAE | RMSE log1p | Spearman | top-1% recall |
|---|---|---|---|---|---|
| proportional rule a*stars+b (baseline) | 0.7318 | 0.363 | 0.303 | 0.463 | 0.673 |
| Poisson GLM | 0.6586 | 0.341 | 0.266 | 0.428 | 0.674 |
| Poisson GBDT (prespecified; diverged, truncated to 0 trees) | 2.3976 | 0.625 | 0.432 | n/a | 0.058 |
| **Poisson GBDT, regularised (amendment 1, kept)** | **0.5361** | **0.287** | **0.247** | 0.441 | **0.684** |

Bootstrap comparisons: kept minus baseline is -0.196 [-0.213, -0.178]; kept minus GLM is -0.122 [-0.154, -0.094].

On the 293,723 test rows whose repository was not in train, the kept model scores 0.376 against 0.525 for the
baseline. The proportional rule ranks slightly better by Spearman (0.463 against 0.441), but the kept model is better
on deviance, MAE and the top-1% recall.

The NB2 dispersion fitted on train is 0.848. Simulated test draws reproduce the observed distribution: share of zero
counts 0.898 against 0.907 observed, P(≥10) 0.0061 against 0.0058, q99 6 against 6, q99.9 40 against 34. The KS
distance on log1p is 0.009, against 0.023 for Poisson draws.

**Descriptive reference (not fitted).** 205,095 repositories were created on D1. Of these, 0.57% received at least
one non-owner star within 24 h and 0.74% within 48 h. They averaged 0.030 stars by 48 h, and q99.9 of stars at 48 h
is 3. The hourly cumulative curve is in the growth report under `new_repository_adoption_curve`.

**What the simulator may and may not infer.** The simulator may use these models:

* as reference rates for light-to-deep engagement over a 24 h horizon;
* for the shape of short-horizon star dynamics: persistence, heavy tails, NB2 overdispersion.

It may not use them:

* for causal effects of promotion, ranking or buying stars (the data are observational);
* for long-run adoption, retention or use by execution;
* for usefulness. Stars are not adoption evidence (MASTER_SPEC 6.5).

Repository ages above about 72 h lie outside the data.

## Scientific record

* **Prespecification.** `registry_e2.prespecified_before_fit(model)` checks, through git, three things: the plan and
  the amendment were each committed before the fit's recorded start; neither changed afterwards; and their hashes
  match the card. All three models pass.
* **Amendment 1** was written after run 1, and run 1's test numbers had already been computed (disclosed in the
  amendment). Its changes follow from numerical divergence that is visible on the training and validation splits,
  and they apply to every GBDT candidate alike. Run-1 cards and reports are kept in `superseded/E2_run1/`.
* **Post-fit diagnostic, not prespecified.** The covariate-balance analysis does not change any model or selection.
  It does change how the commercial average effect should be read, and the card's identification statement and
  limits now say so.
* **Provenance of the final fits.** The fits ran at commit `d0b2a4a`. The software fit's tree was clean. The
  commercial fit's tree held three uncommitted non-code files, all recorded in the card's `fit.dirty_paths`: a test
  marker, REPRODUCE.md and this guide.
* **Gate F quantities over E2's three models** (`registry_e2.gate_metrics()`):
  * 2 empirical domains, 3 held-out reports, 3 baseline comparisons, 3 calibration reports;
  * 3 checkpoints with 0 hash mismatches;
  * 2 datasets with checksums and provenance;
  * 3 extrapolation-limit sections, 0 synthetic-only domains;
  * plans prespecified, `worse_model_kept` = 0.

  Gate F needs three domains and three datasets; E1's content-consumption model supplies the third of each.

## Limitations

* `registry_e2` duplicates E1's registry interface, because E1's registry did not exist in this worktree. Both are
  meant to read the same model-card layout. The card schema is `crucible.v5.calibration.model_card/1`, with the
  fields listed in `REQUIRED_CARD_FIELDS`.
* Nothing in the simulator consumes these models yet. The population (B), social (C) and innovation (G) workstreams
  must wire `simulator_mapping` into their modules, and record decisions as events, for example by storing the type
  index in a population column.
* Uplift ranking: the kept commercial model is selected by log loss, as prespecified. On Qini it does not beat
  T-logistic.
* The report's simulated-experiment check and its exposure Wald estimate both compare with the unadjusted test
  arms. Because the arms differ in composition, neither measures the table's fidelity. Use the type-level validation
  and the standardised estimates instead (see Identification). The card records the commercial fit's dirty paths
  with the first character of the first path cut off ('rucible/...'); `fitmeta_e2.code_state` has since been
  fixed.
* GH Archive covers four weekdays in one week. All conversion and growth horizons are 24 h.
* Running the tests requires the datasets under `$CRUCIBLE_DATA`. They fail, and do not skip, when the data are
  missing.
