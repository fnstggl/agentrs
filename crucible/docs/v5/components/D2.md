# D2: shared small-model inference and semantic participants

Workstream D2 of Crucible 5.0 (package `crucible.semantic`, shared with D1, which owns encoders, cache and media).
It covers MASTER_SPEC 3.2 class 4, 13.4 and Gate H, and the SP-3.2b model-size benchmark. All numbers below were
measured on this machine (RTX A6000 shared with other tenants, at most 4 CPU threads per job, through
`crucible.scale.slots`). Official evidence is produced later on the integration branch by the gate tests.

## What exists

| file | what it is |
|---|---|
| `src/crucible/semantic/service.py` | `SemanticService` (contract 4): one weight copy per (model, revision, device, dtype, quantization) per process, batched generation, option scoring, prefix KV cache, bounds, versioning, recording |
| `src/crucible/semantic/recording.py` | kernel module `semantic_inference` (host `admin`, operator only): records model calls made between transactions, so the world log holds them and replay or regeneration never runs the model |
| `src/crucible/semantic/modules.py` | imports `recording` for `crucible.load_all_modules()` |
| `src/crucible/semantic/participants.py` | `SemanticParticipant` (a `crucible.agents.base.Policy`), `SemanticGroup` (the `batch_group` that decides co-acting participants with one batched call per step), `BatchedRunner`, `select_options`, `consequential_actions` |
| `src/crucible/semantic/scenarios.py` | the Gate H society: eight participants with their own goals in a 4.0 `open_digital` world, plus evaluator-side verifiers that read only world state |
| `src/crucible/semantic/capbench/` | SP-3.2b: `tasks.py` (evaluation sets built in kernel worlds), `models.py` (candidates), `run.py` (statistics, recommendations), `python -m crucible.semantic.capbench` |
| `tests/test_v5_semantic_service.py`, `tests/test_v5_semantic_participants.py` | unit and integration tests (real SmolLM2-135M on the CPU) |
| `tests/v5/test_gate_H.py`, `tests/v5/test_gate_SP_3_2b.py` | gate tests: one test per requirement, each records evidence |

## The inference service

```python
from crucible.semantic.service import SemanticService
svc = SemanticService("Qwen/Qwen3-0.6B", device="auto", max_batch=16, max_new_tokens=640)
svc.generate(None, [{"messages": [...], "max_new_tokens": 64, "temperature": 0.0, "seed": 0,
                     "prefix_messages": 1}])          # -> [{text, prompt_tokens, gen_tokens, finish, truncated, prefix_tokens}]
svc.choose(None, [{"messages": [...], "choices": ["bank.transfer", "mail.send"], "normalize": "mean"}])
                                                      # -> [{choice, logprobs, prompt_tokens, option_tokens}]
svc.info()   # {model_id, revision, params, weights_hash, device, dtype, quantization, ...}
svc.usage()  # counters, tokens_per_s, peak_vram_mb
```

* **One weight copy.** Every `SemanticService` naming the same (model, revision, device, dtype, quantization) uses
  the same loaded weights (`service.loaded_copies()`); participants hold no model state.
* **Batching.** Requests are grouped by shared prefix and greedy/sampled, sorted by length and decoded in batches of
  `max_batch` rows, left-padded after the shared prefix with explicit position ids. Finished rows leave the batch.
  Greedy outputs are identical to one-at-a-time Hugging Face `generate` (tested).
* **Bounds.** Each request's `max_new_tokens` is capped by the service's; prompts by `max_context` (head and tail
  kept, flagged `truncated`). `SemanticGroup` refuses participants whose reasoning budget exceeds the service bound
  instead of letting it be cut silently.
* **Prefix KV cache.** `prefix_messages: k` declares the first k messages shared (participants share the system
  prompt). Its KV cache is computed once, kept in an LRU on the shared weights and expanded to the batch. Without a
  declaration, a group's longest common token prefix is used when it is at least 32 tokens. `choose` computes each
  prompt once and scores all its options against that one cache. `measure_prefix_cache(requests)` measures it.
* **Option scoring.** `normalize`: `mean` or `sum` log probability of the option text, or `pmi` (minus the option's
  log probability after a content-free prompt). Per request, `thinking` switches Qwen3's thinking mode and
  `assistant_prefix` continues a partly written assistant turn.
* **Quantization.** `quantization="int8-dynamic"` (CPU only; PyTorch dynamic int8 linear layers). There is no
  int8 GPU kernel in this environment, so GPU weights stay bfloat16.
* **Versioning.** `revision` is the commit of the local Hugging Face snapshot; `weights_hash` is
  `crucible.substrate.inference.weights_hash` (quantized layers are expanded to plain tensors first), cached on
  disk per (model, revision, device class, dtype, quantization) under `$CRUCIBLE_CACHE/semantic/`.
* **Recording.** `generate(ctx, ...)` / `choose(ctx, ...)` inside a handler record through
  `crucible.substrate.inference.recorded`. Policies decide between transactions, so `SemanticGroup` records each
  batch with `recording.record_inference(world, service, kind, requests, principals)`: the full requests are staged
  in `world.runtime` (never in the log), and the operator-only command `admin.semantic_infer` records the outputs and
  emits `semantic.inference` (internal visibility) with the model id, weights hash, participants and token counts.
  The command event carries only request digests and bounds. `World.regenerate` and `World.replay` reproduce the
  hash chain without running the model (tested with the model call patched to fail).
* **Local only.** Weights are loaded with `local_files_only=True`; nothing in the service touches the network.

## Semantic participants

```python
from crucible.semantic.participants import SemanticGroup, BatchedRunner
group = SemanticGroup(svc, world)                 # world must include the semantic_inference module
agents = [(pid, group.participant(goal)) for pid, goal in ...]
BatchedRunner(world, agents, dt=600).run(24)      # or AsyncRunner: group is the batch_group
```

Each participant has its own principal, goal, memory (observed events and own results) and history; only the
weights are shared. A turn is one tool call, decided in batched steps across all participants deciding together:

1. **Context.** Goal, current state (balances, unread mail), the last four actions with results or errors, and the
   memory items BM25 ranks most relevant to the goal and the latest events, within 1,800 characters.
2. **Candidates.** The tools the participant found with its own `world.find_tools` calls, the available tools most
   relevant to its goal (BM25 over names, descriptions and argument names), the tools relevant to the newest
   events, then `world.find_tools` and `wait`. Read-only calls whose answer is already known (same arguments,
   nothing new since) and tools that failed twice in the last four turns are left out for now.
3. **Tool choice** (`choice_method="think"` for Qwen3): the model reasons in its own thinking mode (at most 384
   tokens) and names a tool; if the text after its reasoning names none, the candidates are scored after the closed
   reasoning. Models without a thinking mode score the tool names (`mean`).
4. **Arguments** (`arg_mode="structured"`): schema-guided, one argument at a time, batched. Enums and booleans are
   chosen among the schema's values (optional ones may be left out); identifiers and numbers are chosen among the
   values in the participant's own goal and observations, or written when "a value not listed" is chosen; text and
   objects are written. Required arguments are always filled; other optional arguments are left out.
   `arg_mode="json"` writes the whole JSON object instead. Invalid arguments are not repaired: the kernel rejects
   the call and the error reaches the next prompt.

No goal, tool sequence or argument value is scripted anywhere; the scaffold is the same for every goal.

| H.8 | peak VRAM 5,813 MiB (society plus measurements); 252 generated tokens/s on the GPU over 1,286 rows in 144 batches (8.9 rows per batch); 1.17M prompt tokens of which 200,616 reused from the prefix cache; CPU (fp32, 4 threads): 6.5 tokens/s for a batch of 8 argument prompts; society wall time 390 s |

A second run of the gate after merging the substrate (recording through `substrate.inference.recorded`) reproduced
every count above exactly (same actions, same 1,166,818 prompt and 147,823 generated tokens, same verified goals).

The prefix-cache measurement on eight argument prompts gave a speedup of 1.00-1.07: the shared system prompt is about 150
tokens against prompts of 700-1,300 tokens, and decoding dominates. Five of the eight outputs were identical with
and without the cache; in bfloat16 the batched prefix computation changes the last bits of the logits, and greedy
decoding can then diverge. Outputs are recorded, so this does not affect replay.

### SP-3.2b (`tests/v5/test_gate_SP_3_2b.py`, 40 min wall)

Evaluation sets (`capbench/tasks.py`): eight capabilities, train 240 / dev 40 / test 120 items each (programming
23 / 6 / 38, from 24 sandbox-tested tasks). Items are staged in `open_digital` worlds by real tool calls (documents
created and read, mail delivered, invoices, contracts, invites, forum replies, failed calls, the world's own tool

programming) come from templates never used for training or development. Generated mail is checked for the
required facts and coherence; generated programs are executed in the Crucible sandbox against hidden tests;

Reading: Qwen3-0.6B is the smallest model that is effective on the capabilities participants use on every turn
(understanding what they read, choosing tools) and stays within the 0.5-1B target, so it remains the default
(DECISION_LOG D-6). Writing programs, negotiating and strategic decisions need Qwen3-1.7B; a task-specific trained
head is enough only for situations of the kinds it was trained on. The service already shares one weight copy per
model, so a combination (0.6B by default, 1.7B for those three capabilities) costs one extra copy of 3.4 GB.

## How to run

```bash
cd crucible
PYTHONPATH=src python -m crucible.scale.slots --cpu 2 --gpu-mb 0 --label "ws-D2: tests" -- \
    python -m pytest -q tests/test_v5_semantic_service.py tests/test_v5_semantic_participants.py
PYTHONPATH=src python -m crucible.scale.slots --cpu 4 --gpu-mb 7000 --label "ws-D2: gate H" -- \
    python -m crucible.acceptance.v5 run --gate H
PYTHONPATH=src python -m crucible.scale.slots --cpu 2 --gpu-mb 10000 --label "ws-D2: SP-3.2b" -- \
    python -m crucible.acceptance.v5 run --requirement SP-3.2b
PYTHONPATH=src python -m crucible.scale.slots --cpu 2 --gpu-mb 10000 --label "ws-D2: benchmark" -- \
    python -m crucible.semantic.capbench --out /tmp/sp32b.json      # the benchmark alone
```

Models needed in the local Hugging Face cache (`$HF_HOME`): Qwen/Qwen3-0.6B and Qwen/Qwen3-1.7B (present),
HuggingFaceTB/SmolLM2-135M-Instruct, HuggingFaceTB/SmolLM2-360M-Instruct and
sentence-transformers/all-MiniLM-L6-v2 (downloaded once, 1.09 GB together; Apache-2.0 like the Qwen3 models).
Built evaluation sets are cached under `$CRUCIBLE_DATA/semantic/capbench/` (keyed by the generator sources).

## Limitations

* The participants are weak agents: in the Gate H run 74 of 129 calls were rejected and 2 of 8 goals were met;
  no document, program or two-sided exchange was produced by Qwen3-0.6B. An earlier diagnostic run with Qwen3-1.7B
  (12 rounds, before the fix that feeds `world.find_tools` results back into the candidates) met 1 goal. Tool choice clears the 0.6 threshold by a small margin (0.608, 95% CI
  0.519-0.691).
* The Gate H society runs in a 4.0 `open_digital` world: the v5 standard population profile (workstream B) is not
  merged. `build_society(family=...)` takes any world family.
* Thinking mode multiplies the generated tokens per decision (about 380 per tool choice); the society is
  decode-bound (252 tokens/s for 0.6B on the shared GPU) and the token-by-token loop is plain PyTorch (no CUDA graphs
  or paged KV cache).
* The prefix cache saves prefill only; with a 150-token shared prefix it did not change wall time.
* CPU execution is feasible but slow for participants (6.5 tokens/s, fp32, 4 threads); int8 dynamic quantization
  works on CPU (tested) but was not benchmarked for quality.
* The evaluation sets are template-generated from world situations; templates and options are written by the
  workstream, and some distractors are plausible (for example `ops.respond` for "answer them"). Test sizes give
  intervals of about plus or minus 0.09.
* Communication is checked automatically (facts present, length, repetition, word ratio), not by a reader.
